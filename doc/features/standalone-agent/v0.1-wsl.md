# Standalone Agent v0.1 — WSL Provider

## Obiettivo

Dimostrare il modello minimo dello Standalone Agent su Windows 11 usando WSL come primo provider reale.

La v0.1 non deve risolvere tutte le combinazioni possibili dell'host e non deve sostituire ancora l'installer corrente. Deve dimostrare che un Agent standalone può osservare lo stato della macchina, produrre un Machine Capability Profile, pianificare e applicare un cambiamento controllato, gestire almeno un reboot/resume e verificare funzionalmente l'environment risultante.

## Backend configuration strategy

La v0.1 non deve implementare un configuration manager proprio.

Il core usa un contratto astratto `ConfigurationBackend`, concettualmente:

```text
inspect()
plan()
apply()
verify()
```

La baseline da prototipare per il caso WSL è:

- **Salt** come primo backend generico e portabile;
- **WinGet/DSC** come backend/helper Windows-specifico quando conviene delegare Windows Optional Features, package o configurazioni native.

Puppet, Ansible, Chef, Nix e altri backend restano compatibili con il modello e potranno essere implementati successivamente senza cambiare i contratti pubblici della v0.1.

## Scope v0.1

La v0.1 comprende soltanto:

1. binario standalone;
2. doctor host minimo;
3. Machine Capability Profile minimo;
4. WSL Provider;
5. Change Plan minimale;
6. apply + verify;
7. reboot/resume minimo;
8. esposizione finale della capability `shell-environment` su Linux tramite WSL.

Non comprende ancora:

- Docker/container provider;
- VirtualBox/Vagrant;
- gestione centralizzata del laboratorio;
- Live/PXE;
- remote execution;
- physical lab;
- topology/network lab;
- ranking/fallback sofisticato;
- capability catalog completo.

## E2E target

```text
Windows host
   ↓
Standalone Agent
   ↓
doctor
   ↓
WSL state detection
   ↓
Change Plan
   ↓
install/repair se necessario
   ↓
reboot/resume se necessario
   ↓
verify
   ↓
shell-environment = AVAILABLE
```

## Verifica funzionale finale

Il provider deve verificare almeno:

- WSL avviabile;
- distro Linux presente e avviabile;
- shell funzionante;
- workspace scrivibile;
- esecuzione di comandi base;
- exit code catturato;
- networking di base quando richiesto dal test.

Micro-lab minimo:

```text
mkdir lab
echo "hello" > hello.txt
cat hello.txt
python3 --version
```

La capability finale deve essere registrata con provider, timestamp e TTL.

## Scenari obbligatori v0.1

1. Windows 11 pulito, WSL assente;
2. Windows 11 con WSL già funzionante;
3. WSL presente ma distro assente;
4. reboot pending / resume;
5. utente senza privilegi amministrativi.

La v0.1 non deve necessariamente riuscire a modificare con successo tutti gli scenari: deve però classificarli correttamente e non lasciare la macchina in uno stato ambiguo.

## Scenari rinviati a v0.2

- virtualizzazione disabilitata nel firmware;
- proxy o reti scolastiche complesse;
- migrazione automatica da vecchie installazioni TheBitLab;
- diagnostica avanzata di corruzioni WSL;
- supporto Windows diverso da Windows 11.

## Stima iniziale

Stima per un MVP credibile, assumendo riuso del codice TheBitLab esistente e senza ampliare lo scope durante l'implementazione:

| Workstream | Stima |
|---|---:|
| packaging standalone spike + baseline | 2–3 giorni |
| Common Core minimo e command surface | 2–3 giorni |
| doctor host + facts Windows | 2–3 giorni |
| Machine Capability Profile v0.1 | 2 giorni |
| WSL probe/diagnose/verify | 3–4 giorni |
| Change Plan minimale + apply | 3–4 giorni |
| reboot/resume persistente | 2–3 giorni |
| test automatici e fixture | 3–4 giorni |
| test su PC reali + hardening | 4–6 giorni |

Totale indicativo: **23–32 giornate/uomo**, cioè circa **4–6 settimane** per una persona con continuità ragionevole. Una prima demo E2E può arrivare prima; il gate v0.1 richiede però prove su host reali e hardening.

## Task proposti

### T1 — Packaging spike

Confrontare almeno le opzioni più realistiche per ottenere un artifact standalone senza Python/Git preinstallati.

Output:

- decision note/spike report;
- binario che esegue `version` e `doctor`;
- misura startup, dimensione e compatibilità Windows 11.

### T2 — Common Core minimale

Definire command surface iniziale:

```text
thebitlab version
thebitlab doctor
thebitlab machine-info
```

Responsabilità:

- config minima;
- logging;
- storage locale minimo;
- dispatch command;
- schema version.

### T3 — Host Facts Windows

Raccogliere almeno:

- Windows release/build;
- architecture;
- CPU/RAM/disk;
- admin capability;
- virtualization support;
- reboot pending;
- network reachability minima.

Nessuna modifica dell'host.

### T4 — Machine Capability Profile v0.1

Definire schema minimo e serializzazione.

Stati:

```text
AVAILABLE
REPAIRABLE
UNAVAILABLE
UNKNOWN
```

Con:

- provider;
- verified_at;
- ttl;
- reason/details bounded.

### T5 — WSL Provider: probe + diagnose

Rilevare almeno:

- disponibilità feature WSL;
- stato installazione WSL;
- versione;
- distro presenti;
- distro predefinita;
- avviabilità;
- necessità di privilegi/reboot.

### T6 — WSL Provider: verify

Verifica funzionale di:

- shell;
- filesystem scrivibile;
- command execution;
- exit code;
- networking base;
- micro-lab di accettazione.

### T7 — ConfigurationBackend spike + Change Plan minimale

Validare sul caso WSL il contratto astratto `inspect / plan / apply / verify` con:

- Salt come backend generico;
- WinGet/DSC come backend/helper Windows-native;
- mapping dei risultati dei backend verso gli stati canonici dell'Agent.

Il codice WSL-specifico deve restare dietro adapter/backend e non contaminare il core.

Dopo lo spike, implementare il Change Plan minimale.



Separare il piano in due strutture:

- `plan_spec`: immutabile dopo approvazione;
- `plan_state`: mutabile durante apply, reboot, resume e verify.

`plan_spec` deve contenere almeno:

- plan ID;
- schema version;
- target;
- current state osservato;
- desired state;
- steps e transizioni consentite;
- class SAFE/CONFIRM/ADMIN;
- reversibilità;
- reboot richiesti;
- provider/versione;
- digest.

`plan_state` deve contenere almeno:

- current step;
- status;
- timestamp;
- result/error bounded;
- reboot pending;
- resume metadata.

Il provider propone la spec tecnica; il Core la valida e applica le policy comuni. Dopo approvazione, la parte decisionale non viene modificata durante l'esecuzione.

### T8 — Apply WSL

Implementare soltanto le modifiche necessarie agli scenari v0.1, senza trasformare il provider in un gestore universale di Windows.

### T9 — Reboot/resume

Persistenza locale di `plan_spec` e `plan_state` e ripresa sicura dopo reboot.

Verificare:

- stesso plan ID;
- `plan_spec` invariata;
- digest invariato;
- avanzamento registrato soltanto in `plan_state`;
- nessuna duplicazione degli step completati;
- verify finale.

### T10 — Automated tests

Test unitari/contract per:

- state mapping;
- capability profile;
- Change Plan;
- resume;
- WSL command parsing;
- failure classification.

### T11 — Real-machine matrix

Eseguire i cinque scenari obbligatori su host reali o immagini sufficientemente rappresentative.

Conservare per ogni run:

- stato iniziale;
- plan;
- modifiche;
- reboot;
- risultato;
- capability finale;
- log/error code.

### T12 — v0.1 closeout

La v0.1 è chiudibile solo quando:

- artifact standalone utilizzabile;
- doctor non modifica l'host;
- WSL Provider classifica correttamente i cinque scenari;
- almeno il percorso happy-path da WSL assente a `shell-environment = AVAILABLE` è E2E;
- reboot/resume è provato;
- il micro-lab passa;
- errori e stati residui sono diagnosticabili.

## Rapporto con il pilot

```text

→ classi/membership
→ accesso studenti

```

I bug dell'installer corrente che bloccano questo percorso restano P0.
